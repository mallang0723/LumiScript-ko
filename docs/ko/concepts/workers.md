# 워커 풀 (Worker pool)

LumiScript는 메인 Lumiverse 프로세스에서 스크립트를 직접 실행하지 않고, **워커 서브프로세스 풀(worker subprocess pool)**에 나누어 실행해요. 스크립트들을 여러 워커에 분산시키면 특정 스크립트가 오작동(무한 루프, 크래시 등)하더라도 다른 스크립트까지 함께 다운되는 것을 막을 수 있어요. 풀은 스스로 최적화되지만, **설정 → 워커(Workers)**에 있는 3개의 설정값과 1개의 버튼으로 이를 직접 제어할 수 있어요.

## 설정 항목

**워커 수 (Worker count)** (기본값 4, 범위 1–16). 실행할 워커 서브프로세스의 개수예요. 워커가 많을수록 결함 격리(fault isolation)가 향상돼요 — 스크립트가 더 넓게 분산되므로 하나의 불량 스크립트가 영향을 주는 동료 스크립트 수가 줄어들어요. 다만 메모리 사용량이 늘어나요(AsyncFunction 엔진 기준 유휴 워커당 약 50~100MB). 스크립트는 지연 할당 방식으로 워커에 배정되어 고정되며, 호스트는 확장 기능당 최대 16개 프로세스로 제한해요.

**유휴 타임아웃 (Idle timeout)** (기본값 30분). 아무런 작업도 하지 않는(스크립트 실행 없음, 핸들러 호출 없음) 유휴 워커는 메모리를 회수하기 위해 이 시간이 지나면 종료돼요. 해당 워커에 배정된 스크립트에 다음 이벤트가 발생하면 워커가 다시 생성돼요(약 150~300ms의 콜드 스타트 지연 발생). 유휴 축출을 사실상 끄고 싶다면 이 값을 매우 높게 설정하세요.

**메모리 상한 (Memory ceiling)** (기본값 512MB). 모든 워커의 상주 메모리(RSS) *합계*에 대한 상한이에요. 총 메모리가 이 한도를 초과하면, 풀은 총합이 한도 아래로 내려갈 때까지 *축출 대상(eligible)* 워커 — 현재 실행 중인 작업이 없고, 마지막 남은 웜 워커가 아닌 워커 — 를 LRU 방식으로 축출해요. 강제 종료(kill)가 아니라 우아하고 부드러운 방식(graceful eviction)으로 진행돼요.

**풀 리밸런스 (Rebalance pool)** (버튼). 모든 스크립트→워커 배정을 해제해요. 각 스크립트의 다음 실행 시 가장 부하가 적은 워커에 새로 배정돼요. 배정은 기본적으로 고정적이므로, 워커 수를 *늘린* 후에 기존 스크립트들을 새 워커로 고르게 분산시키고 싶을 때 이 버튼을 누르세요.

## 축출은 강제가 아닌 안전한 방식으로 이루어져요

유휴 축출과 메모리 축출 모두 **유휴 상태이면서 고정(pin)되지 않은** 워커만 제거하며, 마지막 남은 웜 워커는 절대 종료하지 않아요. 워커는 활성 등록 상태 — `broadcast.on` 구독, 등록된 도구 또는 매크로, 서랍 탭, RPC 엔드포인트, OAuth 콜백 — 를 보유하고 있는 동안 *고정(pinned)*되어 축출에서 제외돼요. 백그라운드 구독이 즉각 응답할 수 있는 비결이에요([핸들러 수명 주기](handler-lifetime.md) 참고). 반대로, 고정된 워커의 메모리가 커지더라도 강제 축출되지 않으므로, 메모리 상한선은 풀이 도달하고자 노력하는 목표치이지 항상 강제되는 절대적 보장은 아니에요.

## QuickJS는 메모리를 더 많이 사용해요

메모리 상한은 각 워커의 전체 프로세스 RSS를 제한하는데, [QuickJS 엔진](engine.md)을 실행하는 워커는 AsyncFunction 워커보다 훨씬 무거워요: WASM 런타임(기본 약 112MB)에 스크립트별 컨텍스트 힙이 더해져 스크립트별 격리 풀의 경우 최대 약 512MB까지 차지할 수 있어요. 따라서 QuickJS 환경에서는 *동일한* 메모리 상한선이라도 훨씬 더 빈번하게 축출과 재생성이 일어나요. 여러 워커에서 QuickJS(특히 스크립트별 격리)를 실행하는 경우, 과도한 재시작을 방지하기 위해 **메모리 상한을 높이거나**(또는 워커 수를 줄이는 것) 하세요. 이 상호작용이 QuickJS를 쓰는 순간부터 이 설정들을 함께 고려할 가치가 있는 가장 큰 이유예요.
