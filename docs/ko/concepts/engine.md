# 실행 엔진 및 격리 (Execution engine & isolation)

여러분의 스크립트는 샌드박스 내부에서 실행돼요. v2.0부터 이 샌드박스는 두 가지 방식으로 제공되며, 그중 하나에서는 스크립트 간 격리 수준을 선택할 수 있어요. 둘 다 **설정 → 스크립트 실행(Script Execution)**에 있는 전역 설정이에요. 기본 설정값으로도 충분히 훌륭하지만, 동작 방식을 이해하거나 설정을 바꾸고 싶을 때 이 문서를 참고하세요.

## 두 가지 엔진

**AsyncFunction** (기본값)은 각 스크립트 본문을 LumiScript 워커 서브프로세스 내부에서 새로운 `new AsyncFunction(...)`으로 실행해요. 매우 빠르고 오랜 검증을 거쳤으며, 첫날부터 모든 스크립트가 실행되어 온 기본 엔진이에요. 동일 워커 내의 모든 스크립트는 해당 서브프로세스의 단일 JavaScript 렐름(realm)을 공유해요.

**QuickJS (실험적 격리 엔진)**은 동일한 워커에 내장된 QuickJS-WASM 가상 머신 내부에서 각 본문을 실행해요. 훨씬 강력한 샌드박스예요: 사용자 코드가 사후에 잠긴 환경이 아니라 애초에 호스트 런타임에 대한 참조가 전혀 없는 별도의 WASM 렐름에서 실행돼요. 관찰 가능한 전체 인터페이스(동일한 `api.*`, 동일한 `data`, 동일한 핸들러 모델)에 걸쳐 AsyncFunction과 동작이 충실하게 일치하며, 이는 이중 엔진 동등성 테스트 스위트로 입증되었어요. 극히 일부의 의도적 차이점은 [API 안정성 → 엔진 간 차이](../api-stability.md#engine-divergence-quickjs-isolate-opt-in)에 정리되어 있으니, 복잡한 스크립트를 전환하기 전에 먼저 확인하세요.

QuickJS를 선택하는 이유: 사용자 코드를 호스트로부터 더 강력하게 격리하고, 컨텍스트별 메모리 상한을 두며, 스크립트별 격리(아래 설명)를 통해 한 스크립트가 다른 스크립트의 샌드박스를 관찰하거나 손상시키지 못하도록 보장하기 위함이에요. 비교적 최신 기능이기 때문에 실험적으로 표시되어 있으며, QuickJS가 충분한 현장 경험을 쌓는 동안에는 AsyncFunction이 기본값으로 유지돼요.

### 엔진 전환하기

**엔진(Engine)** 드롭다운으로 전환할 수 있어요. 등록된 핸들러, 패널, 타이머 등 스크립트의 라이브 상태는 특정 엔진에 종속되어 다른 엔진으로 이전될 수 없기 때문에, 엔진을 전환하면 **모든 활성 스크립트가 다시 로드**돼요:

- **시작(startup) 스크립트는 즉시 다시 실행**돼요(시간차를 두고 순차 실행). 시작 시 생성하는 패널, 알림, LLM 호출이 다시 일어나요.
- **이벤트 기반 스크립트**는 라이브 상태가 초기화되고 다음 트리거가 발생할 때 다시 준비돼요 — 자동 재실행은 되지 않아요.

확인 대화상자에서 설정을 확정하기 전에 어떤 스크립트가 영향을 받는지 정확히 보여줘요. 이 설정은 (스크립트별이 아닌) **전역** 설정이며 영구 저장돼요. 현재 실행 중인 작업은 먼저 기존 엔진에서 완료돼요.

특정 플랫폼에서 QuickJS WASM 모듈을 인스턴스화할 수 없는 경우, 개별 실행은 실패하는 대신 **해당 실행에 한해 AsyncFunction으로 대체(graceful degradation)**돼요 — 설정을 강제로 변경하지 않으므로 이후 실행에서 VM 로드가 가능해지면 스스로 정상화돼요. ([진단](../guides/diagnostics.md) 가이드의 엔진 패널에서 이러한 대체 발생 여부를 확인할 수 있어요.)

## 격리 수준 (QuickJS 전용)

QuickJS 환경에서는 **격리(Isolation)** 드롭다운을 통해 스크립트가 VM을 공유하는 방식을 선택할 수 있어요. AsyncFunction에서는 모든 스크립트를 단일 공유 렐름에서 실행하므로 이 컨트롤이 비활성화되고 *공유 컨텍스트(Shared context)*로 표시돼요.

- **공유 컨텍스트 (Shared context)** (기본값) — 하나의 QuickJS 컨텍스트가 모든 스크립트를 뒷받침해요. 메모리 사용량이 적어요. LumiScript 자체 프레임워크는 동결되어 있으므로, 한 스크립트가 서드파티 라이브러리의 내부를 변조(예: `z.object = evil`)하더라도 그 영향은 *해당 스크립트 자체*의 후속 실행에만 미칠 뿐 다른 스크립트나 호스트에는 도달할 수 없어요.
- **스크립트별 격리 (Per-script isolation)** — 각 스크립트가 고유한 컨텍스트를 받아요: 독립된 `globalThis`, 독립된 `zod` / `Handlebars` / `api` 번들, 그리고 독립된 메모리 상한(제한된 LRU 풀에서 컨텍스트당 약 64MB)을 가져요. 한 스크립트가 다른 스크립트의 샌드박스를 관찰하거나 오염시킬 수 없어요.

격리 설정을 전환하면 QuickJS 워커가 재생성되어 모든 컨텍스트가 새로운 모델에 맞게 재구성돼요 — 엔진 전환과 동일한 재로드 영향이 발생해요. 스크립트별 격리로 설정했다가 나중에 AsyncFunction으로 돌아가더라도 선택 사항은 **보존**돼요: 드롭다운이 회색으로 비활성화되고 *공유 컨텍스트*로 표시되지만, QuickJS로 다시 돌아오는 순간 이전에 선택했던 스크립트별 격리 옵션이 즉시 다시 활성화돼요.

스크립트별 격리는 메모리를 더 사용해요 — 각 컨텍스트가 최대 약 64MB를 예약하며, QuickJS 워커는 일반적으로 AsyncFunction 워커보다 무겁기 때문에 워커 풀이 바쁠 때 메모리 한도에 압박을 줄 수 있어요. 튜닝 방법은 [워커 풀](workers.md)을 참고하세요.

> **`globalThis`의 범위:** 스크립트별 격리 환경에서는 각 스크립트가 *자체* `globalThis`를 가지므로, [저장소 모델](storage-model.md)에서 경고하는 스크립트 간 키 충돌 문제가 발생하지 않아요. AsyncFunction 및 QuickJS *공유* 격리 환경에서는 워커 내의 스크립트끼리 `globalThis`를 공유하므로 반드시 키에 고유한 네임스페이스를 붙여야 해요.

## 스트림 버퍼 (QuickJS 전용)

QuickJS의 `api.llm.generateStream`은 자신을 시작한 실행 수명보다 오래 지속될 수 있으므로 청크 큐에 상한이 적용돼요. **스트림 버퍼 (Stream buffer)** 설정(기본값 512)은 스트림이 에러와 함께 취소되기 전까지 버퍼에 쌓일 수 있는 미소비 청크의 최대 개수를 제한해요 — 느리거나 방치된 소비자가 메모리를 무한정 늘리는 것을 막는 안전장치예요. AsyncFunction에서는 아무런 영향이 없어요. 대용량 데이터를 스트리밍하면서 의도적으로 매우 느리게 소비하는 경우가 아니라면 이 설정을 건드릴 필요가 없어요.

## 동작상의 차이점

QuickJS는 동작이 충실하지만 바이트 단위로 100% 동일하지는 않아요. 자체 `api.tools.invoke` 호출, 순수 `fetch` 응답 형태, `AbortSignal` 처리, 실행된 핸들러 내부 환경 등 현재 알려진 전체 목록은 **[API 안정성 → 엔진 간 차이](../api-stability.md#engine-divergence-quickjs-isolate-opt-in)**에 정리되어 있어요. 복잡한 스크립트를 QuickJS로 옮기신다면 먼저 훑어보세요.
