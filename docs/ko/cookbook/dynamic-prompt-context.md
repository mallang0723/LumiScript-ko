# 매 턴마다 동적 프롬프트 컨텍스트 주입하기 (Inject dynamic prompt context per turn)

매 턴마다 새로운 정보 — 현재 시간, 장면의 진행 깊이, 누적 상태값 — 를 계산하여, 사용자 대화창에는 표시하지 않고 모델이 바라보는 프롬프트에만 몰래 주입하는 패턴이에요. 이는 **스크립트가 타이밍을 직접 소유하는** 프롬프트 컨텍스트 전달 방식이에요: *여러분*이 무엇을 언제 주입할지 정확하게 결정해요.

## 사용할 기능

- `api.chat.inject(id, content, options?)` — 고정된 `id` 아래에 프롬프트 주입 등록. 동일한 `id`로 다시 주입하면 이전 내용이 **덮어쓰기(overwrite)**되어 항상 최신 상태를 유지해요. `interceptor` 권한 필요(기본 매니페스트에 선언됨). ([권한](../concepts/permissions.md))
- `MESSAGE_SENT` 트리거 — 메시지가 생성될 때(사용자가 보낸 메시지는 `data.message.is_user`로 확인) 답변 생성을 위한 프롬프트가 조립되기 직전에 실행돼요. ([트리거 모델](../concepts/trigger-model.md))
- `globalThis` — "매 턴마다 변경됨"을 보여주기 위한 동기식 프로세스별 카운터. ([저장소 모델](../concepts/storage-model.md))

핵심 개념: **주입은 `id`를 키로 관리되며 직접 제거할 때까지 유지돼요.** "매 턴마다 동적 주입"이라는 특별한 모드가 따로 있는 것이 아니라, 매 턴마다 동일한 `id`로 새로 계산된 내용을 넘겨 `inject`를 다시 호출하는 것이에요. 가장 최근 호출이 적용되므로 모델은 항상 최신 값을 보게 돼요.

## 스크립트 코드

```js
// @triggers MESSAGE_SENT
// 각 모델 답변 직전에 새로운 "장면 컨텍스트" 메모를 주입해요.
// 필요 권한: interceptor.
//
// MESSAGE_SENT는 어시스턴트의 빈 플레이스홀더를 포함하여 메시지가 생성될 때마다
// 발생하므로, is_user 가드로 사용자가 전송한 경우에만 실행되도록 해요 (그렇지 않으면
// 아래의 카운터가 턴당 두 번씩 올라갑니다). 사용자 전송 시 답변 프롬프트가 조립되기
// 직전에 실행되므로, 이번 턴의 생성에 반영되도록 메모를 계산하고 동기식(inject 전에 await 없음)으로
// 주입해요 — "동작 원리" 참고.
if (!data.message.is_user) return;

// 1. 메모를 동기식으로 계산 — 턴마다 달라지는 값들.
const now  = new Date();
const hour = now.getHours();
const band =
  hour < 6  ? 'the dead of night' :
  hour < 12 ? 'morning'           :
  hour < 18 ? 'afternoon'         :
              'evening';

// 프로세스별 대화 교환 카운터 — 동기식이므로 주입 타이밍을 지연시키지 않아요.
// (스크립트 러너가 재시작되면 리셋됨; 장면 카운터로 충분해요.)
globalThis.lsSceneContext_turn = (globalThis.lsSceneContext_turn ?? 0) + 1;

// 2. 고정된(STABLE) id로 주입하여, 매 턴마다 새로 쌓이지 않고
//    이전 메모를 덮어쓰도록 해요.
const note =
  `Out-of-character context (do not quote verbatim): it is currently ${band} ` +
  `(${now.toTimeString().slice(0, 5)} server time), exchange #${globalThis.lsSceneContext_turn} this session.`;

api.chat.inject('scene-context', note, { role: 'system', depth: 0 });
```

스크립트를 활성화하고 채팅창에서 메시지를 몇 개 보내보세요. 이 메모는 대화 기록에 절대 나타나지 않지만, 모델은 매 턴마다 최신 버전(시간이 흐르고 카운터가 증가함)을 읽게 돼요. 다른 스크립트나 모의 실행에서 `api.chat.getInjections()`를 호출해 보면 `scene-context` 항목의 내용이 메시지를 보낼 때마다 바뀌는 것을 확인할 수 있어요.

## 동작 원리

**재주입을 통한 갱신; `id`가 고유 식별자예요.** `inject('scene-context', …)`는 `scene-context`라는 슬롯을 등록하거나 대체해요. 별도의 "update" 메서드는 없어요; 덮어쓰는 것이 곧 업데이트예요. 본문이 매 전송마다 다시 실행되므로 슬롯은 항상 이번 턴의 메모를 유지해요. 매번 무작위 ID를 사용하면 이전 메모가 교체되지 않고 매 턴마다 새 메모가 누적되어 쌓이게 돼요.

**`MESSAGE_SENT`를 사용하고 동기식으로 주입하는 이유.** 사용자가 메시지를 보낼 때, `MESSAGE_SENT`는 답변 생성을 위한 프롬프트가 조립되기 *직전에* 실행돼요 — 따라서 그 핸들러에서 등록된 주입 내용은 바로 다음 텍스트 생성에서 읽혀요. 시간 여유는 매우 찰나예요: 호스트는 프롬프트 조립의 마이크로태스크 직전에 이벤트를 발생시키므로, 예제처럼 **동기식(synchronous)**으로 주입하면 시간에 맞출 수 있지만, 주입 전에 느린 작업을 `await`하면 조립 타이밍을 놓쳐 *그다음* 턴에 들어가 버릴 수 있어요(주의사항 참고). 또한 `MESSAGE_SENT`는 어시스턴트의 빈 플레이스홀더에 대해서도 발생하므로, `is_user` 가드를 통해 사용자가 메시지를 보낸 턴에만 실행되도록 해야 해요. 모델의 완성된 답변은 별도의 `GENERATION_ENDED` 이벤트에서 도착해요.

**`mode`, `role`, 그리고 `depth`.** 기본값인 `mode: 'intercept'`는 모델에 전달되기 직전에 완전히 조립된 메시지 배열에 주입 내용을 끼워 넣어요 — 신뢰할 수 있으며 별도의 호스트 조율이 필요하지 않아요. (프롬프트 조립 *전에* 어셈블러를 보강하는 `mode: 'context'`도 있지만 호스트 지원에 의존하므로 `intercept`를 권장해요.) `role`은 주입 내용이 실릴 메시지 역할이에요 — 기본값 `'system'`이 OOC(Out-of-character) 메모에 적합해요. `depth`는 배열의 **끝에서부터** 거리를 세어요: `0`은 맨 뒤(가장 최근, 가장 주목도 높음)에 추가되고, `1`은 마지막 메시지 바로 앞에 삽입되는 식이에요. 현재 상태에 대한 메모는 대개 텍스트 생성 지점과 가장 가까운 맨 끝(`depth: 0`)에 두는 것이 좋아요.

**대화 기록을 전혀 건드리지 않아요.** 주입된 메모는 프롬프트를 형성하지만 대화 메시지가 아니에요 — 채팅 이력에 표시되지 않고, 채팅에 저장되지 않으며, 다음 턴에 다시 주입하지 않으면 다음 프롬프트에 남지 않아요. 모델의 눈에만 보이는 컨텍스트를 제공하고 싶을 때 `api.chat.sendMessage` 대신 이 방식을 사용하는 이유예요.

## 내 프로젝트에 맞게 응용하기

- **1회성 주입.** `{ ephemeral: true }`를 전달하면 다음 텍스트 생성이 끝난 후 주입 내용이 자동으로 제거돼요 — 수동으로 `removeInjection`을 호출하지 않아도 정확히 한 번만 반영돼요. "이번 턴에만"이 문자 그대로의 요구 사항일 때 사용하세요.
- **실제 신호 주입하기.** 시계 예제 대신 실제 읽어올 수 있는 값으로 대체하세요: `api.variables.character`에서 읽은 친밀도 점수, 마지막 주사위 결과, 활성 장면 플래그 등. 읽기 작업을 `await`해야 한다면 아래의 타이밍 주의사항을 염두에 두세요 — 주입 전에 미리 계산해 두거나 1턴 지연을 감수하세요.
- **최근 대화 요약 주입하기.** `api.chat.getMessages({ last: 6 })`로 최근 메시지를 가져와(`chat_mutation` 필요), 휴리스틱이나 `api.llm.generateStructured`로 요약한 뒤 요약본을 주입하세요. 비동기 작업이 필요한 경우 고정된 `id`를 유지하면 비록 1턴 전의 내용일지라도 모델이 항상 컨텍스트를 파악할 수 있어요.
- **다른 주입 방식 선택하기.** `inject`는 *여러분의 스크립트*가 타이밍을 주도할 때 적합해요. 반면 사용자가 프리셋 안에서 원하는 위치에 값을 자유롭게 배치하게 하려면 `{{macro}}`([커스텀 매크로](../guides/macros.md))로 노출하고, 월드북의 키워드 매칭으로 활성화되게 하려면 동적 엔트리([월드 인포](../guides/world-info.md))를 사용하세요. 목표(스크립트가 계산한 컨텍스트)는 같지만 제어 방식은 세 가지로 달라요.

## 주의사항

- **비동기 `await` 작업은 현재 턴을 놓칠 수 있어요.** `intercept` 모드는 *프롬프트 조립 시점*에 슬롯에 들어 있는 내용을 읽는데, 조립은 `MESSAGE_SENT` 발생 직후 순식간에 일어나요. 시계 예제 같은 동기식 연산은 시간 내에 안전하게 들어가요. 하지만 주입 전에 느린 작업(LLM 호출, 네트워크 요청, 심지어 저장소 읽기까지)을 `await`하면 프롬프트 조립이 이미 끝나버려 주입한 내용이 *다음* 턴의 프롬프트에 들어가게 돼요. 주입 로직을 동기식으로 유지하거나, 고정된 `id`로 슬롯을 계속 채워 두면서 1턴의 지연을 수용하거나(대개 괜찮아요), 무거운 연산은 이전 턴의 `GENERATION_ENDED`에서 미리 수행해 두세요.
- **`MESSAGE_SENT`는 사용자 메시지뿐 아니라 모든 메시지 생성 시 발생해요.** 어시스턴트의 빈 플레이스홀더, 인사말, 수동 삽입 메시지에도 발생하므로 사용자 전송에만 반응하려면 반드시 `data.message.is_user` 가드를 두세요. 모델이 말을 *마친 후*에 반응하고 싶다면 `GENERATION_ENDED`를 사용하세요(페이로드는 `{ generationId, chatId, messageId, content }`이며 `message` 객체가 없음).
- **`allowDangerous`가 아니라 `interceptor` 권한이에요.** `api.chat.inject`는 `interceptor` 권한만 필요해요. 이 계열 중 추가로 `allowDangerous`가 필요한 유일한 메서드는 *모든* 스크립트의 주입을 지워버리는 `clearAllInjections`예요(자신의 주입만 지우는 `clearInjections()`는 권한 불필요).
- **`depth`는 앞이 아니라 뒤에서부터 계산해요.** `depth: 0`은 배열의 맨 앞이 아니라 맨 끝(가장 최근 메시지 뒤)이에요. 메모가 예상치 못한 위치에 삽입된다면 방향을 반대로 생각했을 가능성이 커요.

## 관련 항목

- [트리거 모델](../concepts/trigger-model.md) — `MESSAGE_SENT` (메시지 생성 시 발생 — `is_user` 가드 필요, 조립 전) vs `GENERATION_ENDED` (어시스턴트 생성 완료 텍스트).
- [권한](../concepts/permissions.md) — `interceptor` 권한이 제어하는 범위와 권한이 거부되면 동작이 어떻게 축소되는지.
- [커스텀 매크로](../guides/macros.md) 및 [월드 인포](../guides/world-info.md) — 프롬프트에 스크립트 계산 콘텐츠를 주입하는 다른 두 가지 경로.
- [저장소 모델](../concepts/storage-model.md) — 주입할 상태를 턴 사이에 보관하기에 적합한 저장소 선택.
